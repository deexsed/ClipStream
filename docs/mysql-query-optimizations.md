# Оптимизации запросов MySQL

Три изменения используют существующие индексы и не требуют миграции БД:

- `SyncRepository::dashboard()` один раз агрегирует импорты за 24 UTC-часа по `created_at`, затем присоединяет результат к плотному ряду часов. Интервал начинается за 23 часа до начала текущего часа и заканчивается началом следующего часа; пустые часы возвращают ноль. Скрытые и недоступные клипы учитываются как факты импорта.
- `ClipRepository::refresh_dirty_recommendation_features()` сначала выбирает до 200 ID по `(queued_at,clip_id)`, затем получает `generation` по первичному ключу. Удаление обработанных записей по паре `(clip_id,generation)` сохраняет события, поступившие во время пересчёта.
- `ClipRepository::find_filtered()` фильтрует и сортирует по STORED generated column `twitch_created_ts`. Сохраняются пороги просмотров, сортировка с учётом промо, ограничения видимости, mutes и пагинация. NULL/пустые даты исключены из ограниченных периодов, но допустимы в `all`; нормализация пробелов определяется существующим выражением generated column.

## Контрольный замер

17 ноября 2026 года выполнены 30 планов `EXPLAIN ANALYZE` на MySQL 8.0.46 с каталогом примерно 94 тысяч клипов. Исходный и изменённый запросы сравнивались по три раза на одном read-only snapshot при фиксированном времени SQL-сеанса. Медианы:

| Запрос | До, мс | После, мс |
| --- | ---: | ---: |
| Почасовой график импорта | 1418 | 62 |
| Очередь пересчёта, 200 записей | 7,41 | 0,288 |
| Сегодня, recent, 24 клипа | 111 | 37,8 |
| Сегодня, popular, 24 клипа | 131 | 42 |
| Всё время, recent, 24 клипа | 169 | 143 |

Результаты графика и очереди, а также ID и порядок клипов совпали. Новый план графика выполняет один covering index range scan вместо 24 повторных просмотров каталога; очередь читает 200 записей индекса и получает generation по PK; период Today использует `idx_clips_feed_ts`. Для `all` полный просмотр и сортировка сохраняются. Значения отражают локальные условия с параллельным импортом и сборкой, не являются p95/p99 или гарантией задержки API.

## Регрессионные тесты

CTest `query_optimization_contracts` вызывает реальные методы repository и проверяет границы часов и периодов, пустую статистику, порядок очереди с одинаковым временем, лимит 200, сохранение новой generation, промо, mutes и скрытие клипов. Изменение generation моделируется test-only trigger при записи признаков, без зависимости от планировщика потоков. Временные пороги производительности не используются.

Нужна отдельная пустая MySQL 8 database с именем, заканчивающимся на `_test`. Задайте `CLIPSTREAM_QUERY_TEST_DATABASE`, `MYSQL_HOST`, `MYSQL_PORT`, `MYSQL_USER`, `MYSQL_PASSWORD` и `MIGRATIONS_DIR`. Пользователь тестовой БД должен иметь права на миграции и CREATE/DROP TRIGGER. Redis для этого теста не требуется. Тест сам применяет миграции, фиксирует часы SQL-сеанса и очищает свои fixtures. Не используйте рабочую БД или БД других одновременно запускаемых suites.

```sh
cmake --build backend/build --target query_optimization_contract_tests
ctest --test-dir backend/build -R '^query_optimization_contracts$' --output-on-failure
```

Если `CLIPSTREAM_QUERY_TEST_DATABASE` не задана, suite возвращает skip code 77. Отдельная переменная предотвращает вмешательство в fixtures других integration tests.

17 ноября 2026 года выполнена Release-сборка всех backend targets в Linux-контейнере (GCC 11.4, C++20). CTest с отдельными MySQL/Redis: **12/12 PASS, без пропусков**, включая новый suite; полное выполнение тестов заняло 9 секунд. Проверка clang-format нового теста и `git diff --check` прошли. Нативная сборка Windows и развёртывание работающих API/worker в эту проверку не входили.

Для измерения производительности используйте `EXPLAIN ANALYZE` на актуальных SELECT с представительными данными. Сравнивайте исходную и изменённую версии в одном read-only consistent snapshot при фиксированном `timestamp`; сохраняйте планы и количество просмотренных строк. Время зависит от объёма данных, прогрева кеша и параллельного импорта; оно не является гарантией HTTP latency.

В `find_filtered()` сортировка и пагинация выполняются по ID и ключам ранжирования. Полные поля клипа и имя игры загружаются после `LIMIT`. При равных ключах клипы упорядочиваются по ID по убыванию. Для ошибки на этапе выбора страницы API пишет в лог код MySQL, период, сортировку, размер страницы, смещение и время выполнения без текста фильтров.

Для недельной ленты «Сначала новые» без поиска, категории, канала и тега `find_filtered()` использует `idx_clips_recent_order` из миграции 013. Запрос берёт `offset + limit` подходящих клипов в порядке даты и добавляет все остальные клипы с той же датой, что у последнего отобранного клипа. Затем он применяет порядок по промо, просмотрам и ID. Так граница страницы не отсекает клипы, которые могли бы подняться выше при равных датах. Фильтры видимости и пользователя применяются до отбора, включая выборку на границе.

Контрольный замер на 105 882 клипах в MySQL 8.0.46. Перед каждым из шести запросов перезапускались MySQL и API, кеш файлов тестовой БД сбрасывался, Redis был пуст. У старого плана `EXPLAIN ANALYZE` показал полный просмотр каталога. Медиана первого HTTP-ответа (три запуска на версию) снизилась с 2,83 до 1,16 с, время выбора страницы в MySQL — с 2,62 до 0,98 с, чтение InnoDB за запрос — с 70,55 до 1,17 МиБ. Все шесть ответов вернули те же 12 ID в том же порядке. Регрессионный тест проверяет промо на границе даты, фильтры, смещение и пустую страницу. CTest прошёл 12/12.
